## Proposed execution flow

1. Discover the selected workspace repositories. React to editor Git API events as signals and check commit state through the Git CLI (agreed A19).
2. After the CLI shows the worktree tip moved by a commit, amend, merge, pull, or finished rebase, show one notification naming that verified commit. Checkout, reset, and staging stay quiet. Starting the review is an explicit Start action. An open review stays on its pinned commit.
3. At review start, pin the selected full commit ID and its comparison base throughout the session (agreed). Use the sole direct parent for a single-parent commit, the recorded first parent for a merge, and an empty tree for a parentless root commit. Read committed code using these fixed identities.
4. The extension gathers the agreed initial input from the pinned Git versions: fixed identities, a permitted changed-file inventory, textual diffs, and bounded surrounding code with before/after references. Call the agreed AI interface through an isolated Codex SDK thread (agreed A13): neutral working directory, ignored user and project config, read-only, network and web search off. The AI may request additional code through bounded structured List paths, literal Search text, and Read lines operations; the validator checks requests and the Git/context reader retrieves approved code. Start with two additional rounds per operation, counting a file batch as one round. Each original operation uses a new short-lived thread (agreed A14). Offline simulations supply a fake implementation to the same controller. Excerpt sizes and total-work caps remain pending.
5. First Codex proposes consequential technical decisions supported by specific code, with useful reasoning and credible alternatives/tradeoffs. For oversized commits, analyze manageable chunks and consolidate the candidates across them before presenting the outline, merging the same underlying decision into one highlight. Do not force a quota; allow zero highlights and report that no major technical decisions were identified when appropriate. Label inferred rationale and attribute author intent only when repository evidence supplies it. Planned analysis must fit the total-work budget; pause with pending coverage reported if it is insufficient. Exact selection prompts/grouping mechanics, chunk mechanics, numerical budgets, and schemas remain pending.
6. Agreed validation policy: require schema-constrained JSON and validate response structure/application consistency in the host, checking selection references against the fixed snapshot. Reject invalid references before display and retain the validated outline within the session. Distinguish examining the commit from discussing every change; report unread or excluded areas honestly. Explicit correction/versioning behavior remains pending.
7. Generate the current highlight on demand: explanation, relevant alternatives, reviewer question, and a frozen rubric prepared before the answer (agreed A16). Apply host validation before presentation and source snippets from the Git snapshot. Render explanation and answer text as plain text. Opening code uses a host-issued reference to the pinned snapshot (agreed A15).
8. Send the first free-text answer for criteria-based assessment. The host computes the percent. The model's own percent is ignored.
9. If the confident host score is at least 80%, show feedback, add only the XP increase, play the in-chat celebration when the score newly reaches that gate, and enable explicit Continue (agreed A18).
10. Otherwise ask one focused follow-up and reassess. For each criterion, keep the stronger finding across the two answers (agreed A16). Uncertainty does not change the score.
11. If the follow-up result is still below 80% or still uncertain, the highlight is unresolved (agreed A17). Continue stays off. Skip records it unresolved and shows the next decision. Close leaves the session on this highlight. The question and criteria stay frozen.
12. Persist the checkpoint as versioned JSON in editor workspace storage (agreed A20) after each accepted transition. On explicit Continue, discuss the next selected decision; after the last, post the recap in the same chat conversation.

Failures remain distinguishable: Git access failure, model failure, invalid model output, uncertain assessment, and insufficient understanding. Each needs recovery without losing verified progress or duplicating points.

The agreed host response-validation layer detects structural and application-consistency errors: Zod checks response shape/types, while application checks use the immutable Git snapshot and prepared criteria. Validation failure triggers the agreed one-correction policy; the application/controller enforces that budget separately from learner follow-ups. A corrected response must pass the same checks. Existing references and valid fields do not prove an explanation is semantically correct; the separate quality evaluations assess that behavior on labelled cases rather than detecting every live mistake. Exact component signatures and wiring remain pending.

On model unavailability, the application pauses, checkpoints verified review state, and prompts the owner to optionally choose another supported model. After an explicit selection it starts a new thread with the structured JSON continuation and resumes the pending work in the same application review (agreed A14). A response already in flight from the old model is discarded. The new model inherits the review's fixed evidence, prepared criteria, recorded answers/progress, privacy scope, and relevant counters. Changing models does not grant a new learner follow-up or alter prior validated results. Record the model transition in the session file. Numerical context and total-work budgets remain pending. No model-switch implementation or live runtime verification has occurred.

## Agreed entities

These are logical TypeScript entities. Selecting them does not require a relational database. The earlier prototype `Lesson` session is not this contract.

| Entity | Important fields | Ownership and relationships |
| --- | --- | --- |
| RepositoryIdentity | id from the Git common-directory path, displayName | One repository has many commits and sessions. Worktrees of the same repository share this id. |
| CommitSnapshot | repositoryId, sha, parentSha, changedFiles, canonicalCodeRanges, comparisonKind | Git is the source of truth. A session references one immutable snapshot. |
| DecisionOutlineItem | id, decision statement, codeRefs | Validated selection before highlight generation. The host assigns ids. |
| ReviewSession | id, repositoryId, commitSha, schemaVersion, highlightIds, currentHighlightId, state | One file per session. A second review of the same commit gets a new id and does not delete the first. |
| ReviewHighlight | id, decisionTitle, explanation, rationaleKind, codeRefs, alternatives, question, criteria | Frozen when presented. Snippet text comes from the Git snapshot. |
| Criterion | id, description, kind, weight | Kind is behavior, reasoning, or tradeoff. Weight is a multiple of 10 from 20 through 50. Prepared and frozen before the answer. |
| AnswerAttempt | id, highlightId, kind, text, submittedAt | Initial answer or the single allowed follow-up. At most two attempts. |
| Assessment | id, highlightId, findings, hostPercent, confidence, feedback | Each finding is missed, partial, or met. The host computes the percent and keeps the stronger finding per criterion. |
| HighlightProgress | highlightId, status, bestScore, followUpUsed | Status includes awaiting answer, follow-up, ready to continue, unresolved, and skipped. |
| RewardRecord | highlightId, earnedXp | Earned XP is the high-water mark of the host percent. |

The webview may send ready, start, submit an answer, retry, continue, and open a host-issued snippet reference. Skip is valid only from unresolved. The host rejects unknown message types and versions. The panel never receives the whole checkpoint and cannot set a score.

Association summary: Repository → CommitSnapshot → ReviewSession → DecisionOutlineItem → ReviewHighlight → Criterion; each highlight also has AnswerAttempt, Assessment, HighlightProgress, and RewardRecord records. Several sessions may reference one snapshot.

## Proposed module boundaries

```text
src/extension/   activation, commands, notifications, controller
src/git/         repository discovery, commit snapshots, canonical code ranges
src/core/        entities, state transitions, score/reward rules
src/ai/          provider interface, Codex adapter, output validation
src/storage/     persistence and version migration
src/shared/      validated host/webview message contracts
src/webview/     React views, code cards, answer/follow-up UI, cosmic rewards
```

The webview sends intents. The host validates them and owns Git, provider execution, assessment processing, and persistence. This split prevents UI events or model text from becoming privileged operations. Model HTML stays text. Remote images are not loaded. Celebration art is bundled.
